## 二、背景与目标

### 2.1 两套系统为什么都不够用

**现状：三套在用系统各自为政。**

| 系统 | 在用范围 | 真实定位 | 主要问题 |
|---|---|---|---|
| 用友 T+ | 财务核算、存货账 | 财务部门的事实标准 | 单据事后补录、滞后失真；存货账做不到账实相符；不含项目/工程维度 |
| 钉钉 | 审批、日志汇报 | 全员协同入口 | 只管流程不管数据；审批单与业务单据两张皮 |
| 售后宝 | 工程派工、现场施工 | 售后服务工具 | 起点在售后；工单人工转录；与合同、发货、设备档案无关联 |

由此形成**六个断点**：报价→合同（报价不回流）、合同→生产（靠开会传）、生产→采购（无 BOM 齐套）、库房出入库（实物先走账后补）、发货→安装（工程部不知道发了什么）、安装→验收回款（靠催）。

**已有方案的两次尝试，各缺一半：**

| 尝试 | 做了什么 | 缺什么 |
|---|---|---|
| **ProjLife 需求体系**（2026-05—08） | 用十大系统维度设计了完整的 ETO 全流程：商机→合同→项目任务→设计→工艺→采购→生产→质量→工程→售后→成本→文件→AI | 不了解这家公司的真实数据长什么样。它假设"库存由 T+ 管所以本地不建表"，却没解决"单据滞后"这个病根；它设计了 EBOM/MBOM/SBOM，却没区分"哪些产品根本不需要 MBOM" |
| **业务总台方案**（2026-08—10） | 用真实数据诊断出六断点、8,764 处 BOM 缺陷、账实 92%、补货 663 次，给出了编码规则、查重、五流一致、九板看板、库房 ABC | 没有设计成能承载十大系统的软件。它止步于"16 个模块 + 九块板"，没有工序级报工、没有排产、没有 SPC/FMEA、没有设备资产管理 |

**本版要做的，是把两者焊在一起：A 的广度 × B 的深度。**

### 2.2 已被数据证实的三件事（设计铁律的来源）

| # | 事实 | 数据证据 | 强制要求 |
|---|---|---|---|
| 1 | **手工填报必然被"月末补写"击穿** | 商务部 9 月 62 条日报，平均编制后 **16.7 天**才提交，**52%** 集中在 10 月 8 日一天补交 | 指标自动取数；人工只维护"异常卡点"（红灯卡），不维护常规进展 |
| 2 | **主数据没有唯一入口，一物多名是系统性的** | 工程逐日台账 2,051 条记录覆盖 100 余项目，暴露 7 类问题；带编码项目仅个位数；T+ 合同号字段 100% 空置 | 所有下游表单的项目/客户/物料字段**只能下拉选择**；建档只有一个入口 |
| 3 | **数据缺陷已造成实质经营损失** | BOM 审计：一码多物 189 处、一物多码 29 组、A 级材质/尺寸真冲突 15 组影响 2,004 行；呆滞 53 托盘/391 种/32,899 件；1—8 月补货 677 行中 **31.9%** 源于内部可控环节 | 主数据校验、BOM 双码检测、齐套检查、补货分级必须是**系统硬校验** |

| 层 | 指标 | 现状基线 | 上线 6 个月 | 口径 |

| 业务 | 月度现场补货次数 | 约 83 次/月 | **≤35 次/月** | 当月补货申请单数 |
| 业务 | 补货审批中位时长 | 9.1 天 | **≤2 天** | 提交到出库中位自然日 |
| 业务 | 订单准时交付率 | 无统计 | 建基线并逐季改善 | 按合同交期实际发货 ÷ 应发货 |

| 能力 | AI 功能使用率 | 无 | 合同分析/提取 **≥80%** 新合同使用 | 使用 AI 的合同 ÷ 新签合同 |
| 数据 | 合同档案完整率 | 无档案 | **≥95%** | 关键 12 项全非空 |
| 数据 | 一物多码月新增 | 持续新增 | **0 组** | 当月新增触发同物异码检查 |
| 数据 | BOM 变更正式单率 | 3.9% | **100%** | 走 ECN 的变更 ÷ 全部变更 |
| 管理 | 红灯卡 3 日闭环率 | 无机制 | **≥80%** | 3 日内摘除 ÷ 新增 |
| 管理 | 协调类会议时长 | 无统计 | 压缩约 **40%**（估算） | 周调度+月度经营合计同比 |

## 三、名词与术语

| 术语 | 定义 | 易混点 |
|---|---|---|
| ETO | 按订单设计/制造/服务（Engineering to Order） | 与 MTO（按订单制造）区别在于设计也定制 |
| EBOM / MBOM / SBOM | 设计/制造/服务物料清单 | 三个**视图**，不是三套物料 |
| A/B/C 类 BOM | 标准产品/参数化产品/系统工程 三种**形态** | 与视图正交，见 00 册 C-09 |
| Golden BOM | 产品级标准 BOM，项目 BOM 只能由其派生 | 治"复制改"的根本手段 |
| 工程 BOM | C 类项目的物料清单，按点位展开 | = A 说的"项目设备材料清单" |
| 设备档案 / 机组档案 | 一台机组装了什么（含序列号、安装位置） | 由 SBOM 沉淀而来，一机一档 |
| 一单到底 | 从报价到回款全程引用同一个 project_code | 系统级设计主线 |
| 五流一致 | 合同流/项目流/资金流/发票流/货物流 | 在原"四流"上补项目流 |
| 硬卡点 | 服务端拒绝提交的强制校验，不可跳过 | 全系统仅 9 处 |
| 红灯卡 | 看板上受阻/超期/待决策的卡片 | 数据实体，不是工单 |
| 四区一栏 | 指标区、进行区、红灯区、闭环区 + 卡片栏 | 九板统一结构 |
| 链主 | 对整条业务链卡点负责的部门负责人 | 与流程 Owner 同一份名单 |
| 三算对比 | 预算 → 目标成本 → 实际成本 | A 用词，等同 B 的"成本三算" |
| EVM | 挣值管理（PV/EV/AC → SPI/CPI） | 项目进度-成本联合监控 |
| CTP / ATP | 可承诺能力 / 可承诺量 | 接单时算交期 |
| OEE | 设备综合效率 = 可用率×性能率×良品率 | SCADA 试点指标 |
| MTBF / MTTR | 平均无故障时间 / 平均修复时间 | EAM 指标 |
| Cpk / Ppk | 过程能力指数 / 过程性能指数 | QMS 指标，Cpk<1.33 触发改进 |
| RPN | 风险优先数 = 严重度×频度×探测度 | FMEA 指标 |
| 8D / CAPA | 八步纠错法 / 纠正与预防措施 | 质量问题闭环 |
| AQL | 可接受质量水平（抽样方案） | IQC 用 |
| 水印四形态 | 页面水印/下载水印/照片水印/小程序水印 | 见 03 册 |
| 端限制 | 第三方施工人员只能登录小程序 | 安全约束 BR-08 |

### 4.3 分期与"必须跑通"的最小闭环

虽然 18 域全做，但**必须有一条端到端链路先跑通**，否则各域都是孤岛：

```
商机 → 合同评审(BR-01) → 用印编号 → 建档备案(BR-02) → 项目立项
  → 任务分解 → 技术条件 → 电气/机械设计 → EBOM → 工艺 MBOM
  → 齐套检查 → 采购 → 到货扫码入库 → 生产工序报工 → OQC
  → 齐套发货 → 派工(BR-03/04) → 施工销项 → 验收 → 开票 → 回款
  → 设备档案 → 售后工单 → 项目关闭
```

这条链路覆盖 12 个域、约 60 张表。**S1—S7 切片的唯一目的就是让它跑通**（见 16 册）。

## 五、方案对比与选型

### 5.1 四条路线的最终对比

| 维度 | A 采购成品（建文云/鼎捷/用友建筑云） | B 低代码平台（简道云/氚云/宜搭） | C 从零定制（外包） | **D AI Agent 定制（选定）** |
|---|---|---|---|---|
| 首年投入 | 30—150 万 + 实施 | 5—15 万 | 40 万起 | 开发投入一次性 + 服务器约 1—2 万/年（含 GPU 或租用） |
| 周期 | 12 个月+ | 3—4 个月 | 6—12 个月 | S0—S9 约 20—26 周（**估算**） |
| 行业匹配 | 建文/广联达强在建筑，无 PLM/MES；鼎捷强在制造，工程现场弱 | 通用，无行业纵深 | 取决于团队 | **完全按本规格包** |
| 复杂规则 | 需二次开发，费用另计 | 编码引擎/齐套算法/排产/SPC 做不动 | 可做 | **可做** |
| AI 内网部署 | 厂商方案多为公网 API，不合规 | 无法内网私有化 | 可做 | **可做** |
| 维护 | 厂商 | 平台 + 内部管理员 | 外包团队 | **公司自有（AI Agent 增量迭代）** |
| 主要风险 | 定制费失控、行业不匹配 | 核心价值被削掉 | 交付后无人维护 | 无专职 IT 时的长期可维护性 |

**选 D 的核心理由**：本系统有五个"低代码做不动、成品买不到"的地方——① 12 类编码引擎；② BOM 二维矩阵（三形态×三视图）；③ 有限产能排产与齐套算法；④ 水印与端限制的文件安全体系；⑤ 内网私有化 AI 网关 + 人工复核闭环。这五处正是本项目的价值所在。

### 5.2 必须接受的四个代价

| 代价 | 表现 | 缓解 |
|---|---|---|
| 无专职 IT，长期维护靠 AI Agent + 规格包 | 上线后改需求需重新拉起 Agent | 规格包即"可维护性资产"；所有假设记 `docs/ASSUMPTIONS.md`；配置项全界面化 |
| 业务不能自助改表单 | 加字段走开发流程 | 预留 `ext_json` 扩展字段机制（见 02 册 §8） |
| 技术栈偏旧（Spring Boot 2.7 / Vue2 均已 EOL） | 安全补丁不再更新 | 内网部署 + 依赖扫描 + 预留升级路径（00 册 C-01） |

### 5.3 演进路径与触发条件

## 十一、权限与安全

**三维模型**：角色（Role）+ 数据范围（SELF/DEPT/ALL/项目成员）+ 操作权限码（`module:action[:object]`）。

| 关键设计 | 内容 |
|---|---|
| 权限码粒度 | 菜单 + 按钮 + 接口；后端 `@RequirePermission("contract:view_price")` 注解 + AOP；前端 `v-permission` 仅控制显示 |
| 数据范围 | MyBatis-Plus 拦截器自动追加 `created_by=?` / `department_id=?` / 项目成员子查询 |
| 第三方隔离 | 供应商只见本企业订单且无价格；施工人员只见授权项目且仅小程序 |
| 脱敏 | 6 类字段按权限返回 null；前端显示 `***`；日志同样脱敏 |
| 文件安全 | 四种水印形态；下载只给带水印 PDF；小程序禁打印 API |
| AI 隔离 | 只有 ai-gateway 能访问内网模型；业务代码不得直连 |

（完整权限码表与 18 角色矩阵见 03 册）
