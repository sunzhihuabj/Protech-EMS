## 一、为什么要有这一版

现在手上有**两套互不相同的需求体系**，各自完整，但没人把它们对齐过：

|      | **体系 A：RPD 文件夹**（2026-05 — 08）                                   | **体系 B：工作目录经营文件**（2026-08 — 10）                    |
| ---- | ---------------------------------------------------------------- | -------------------------------------------------- |
| 名称   | 系统流程管理平台 / ProjLife                                              | 业务总台 / 订单全生命周期管理系统                                 |
| 出发点  | 系统集成工程公司的全生命周期（ETO 模式）                                           | 现有三系统断链 + 六处断点 + 数据体检                              |
| 广度   | 十大系统（CRM/ERP/SCM/WMS/PLM/MES/APS/QMS/EAM/SCADA）+ 工程 + 第三方        | 16 个业务模块（报价→回款→看板）                                 |
| 深度   | 工序级报工、有限产能排产、SPC、FMEA、设备 OEE                                     | 编码规则、查重、五流一致、九板红灯卡、库房 ABC                          |
| 技术   | Java 8/11 + Spring Boot 2.7 + Vue2 + GreatDB + 微信小程序 + 内网 AI 双模型 | 未定（曾建议低代码，后改为 AI Agent 定制）                         |
| 数据基础 | 无真实业务数据                                                          | **有**：7,857 行订单、2,051 条台账、8,913 份工艺文件、77,141 行 BOM |
| 规模   | 122 人 / 200 并发 / 100 QPS                                         | 121 人 / 14 部门 / 9 块看板                              |

**结论**：A 有骨架无血肉（架构与功能面很全，但不了解这家公司真实的数据长什么样）；B 有血肉无骨架（知道哪里疼、怎么治，但没设计成一套能承载十大系统的软件）。

**本规格包做三件事**：

1. **A 的广度 × B 的深度**：用 A 的十大系统维度搭骨架，用 B 的真实数据与业务规则填血肉；
2. **裁决 12 处硬冲突**（下一节），每处给出裁决、理由与代价，不留悬空；
3. **输出一套 AI 编程工具可直接执行的 RPD**（18 册，20 个数据域、150 张表、560+ 条编号需求）。

## 二、12 处硬冲突的裁决（**最重要的一节，先看这里**）

> 每条格式：冲突 → 裁决 → 理由 → 代价/风险。**本表是唯一裁决记录，其他册与本表冲突时以本表为准。**

### C-01 技术栈：两套完全不同的技术路线

|       | A                                          | B（上一版规格包）                        |
| ----- | ------------------------------------------ | -------------------------------- |
| 后端    | Java 8/11 + Spring Boot 2.7 + MyBatis-Plus | Next.js 15 + TypeScript + Prisma |
| 前端    | Vue 2.6 + Element UI                       | React + shadcn/ui                |
| 数据库   | GreatDB（MySQL 8 兼容）                        | PostgreSQL 16                    |
| 缓存/MQ | Redis + RabbitMQ                           | 无                                |

**裁决：采用 A，锁定 Java + Vue2 + GreatDB + Redis + RabbitMQ。**  
**理由**：A 是客户既定技术决策（0517 文档第 2 章标注"强制约束"），涉及信创选型（万里数据库）、内网私有化、现有团队技能。B 的技术栈是我上一版为"AI Agent 独立开发"假设的，没有客户约束力。

**代价与必须知道的三个事实**（写进风险登记册）：

| 风险                               | 事实                     | 应对                                                                              |
| -------------------------------- | ---------------------- | ------------------------------------------------------------------------------- |
| Spring Boot 2.7 已停止开源维护（2023-11） | 存在未修复 CVE 的可能          | 基线用 2.7.18（最后版本）+ 内网部署 + 依赖漏洞扫描；**预留升级到 3.2 的路径**（不用 javax→jakarta 的写法，或统一用兼容层） |
| Vue 2 已于 2023-12-31 停止维护         | 生态不再更新                 | 用 Vue 2.7（最后版本，内置 Composition API），为后续升 Vue 3 留出 setup 写法；**不引入冷门 Vue2 组件库**    |
| GreatDB 与 MySQL 8 的兼容边界          | JSON 函数、窗口函数、CTE 可能有差异 | 全部 DDL/DML 只用 MySQL 8.0 标准语法；禁用 MySQL 8.0.30+ 新特性；上线前跑一遍 GreatDB 兼容性验证          |

### C-02 架构形态：20 个微服务还是单体

| A 的原文                                                                                                                                                 | 现实                                                            |
| ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 拆分 `gateway/auth/crm/contract/project/erp-finance/erp-hr/plm/scm/wms/mes/aps/qms/engineering/eam/scada/document/ai/notification/third-party` 共 20 个服务 | 122 人公司、200 并发、100 QPS；无专职运维团队；A 自己也写"如团队规模较小，可合并为 5-6 个核心服务" |

**裁决：模块化单体（Modular Monolith）+ 3 个旁路服务，共 4 个可部署进程。**

```
projlife-app            主应用（单一 Spring Boot，Maven 多模块，14 个业务模块）
  ├─ module-org         组织/用户/角色/权限/字典
  ├─ module-crm         商机/客户360/漏斗
  ├─ module-contract    合同/评审/交底/收款/AI 分析
  ├─ module-project     项目/任务/ECO/甘特
  ├─ module-plm         勘测/设计/EBOM/MBOM/SBOM/变更/标准件
  ├─ module-process     工艺文件/工时/工艺路线
  ├─ module-scm         供应商/采购/物流/价格库
  ├─ module-inventory   库存对接/库位/条码/盘点/呆滞/补货
  ├─ module-mes         生产订单/工序路由/报工/Andon
  ├─ module-aps         排产/齐套/插单
  ├─ module-qms         检验/SPC/FMEA/8D/量具
  ├─ module-eam         设备台账/维护/备件
  ├─ module-engineering 施工/安装/验收/整改/进度/安全/售后
  ├─ module-cost        成本/预算/三算/EVM
  ├─ module-mdm         主数据/编码/查重/治理/档案
  └─ module-kb          看板/指标/卡片/会议
projlife-ai-gateway     独立进程：唯一能访问内网模型服务器的组件
projlife-file-service   独立进程：OnlyOffice 回调、PDF 转换、水印合成、照片处理
projlife-job-worker     独立进程：定时任务（提醒/升级/指标预计算/对账/预警）
```

**理由**：① 模块边界清晰即可随时拆出，不必一开始付分布式事务与运维的代价；② 单体不是"烂代码"，`module-*` 之间**禁止跨模块直接访问 Mapper**，只能通过 `api` 包内的接口，这是可拆分的前提；③ AI 网关与文件服务必须独立，因为它们的资源特征（GPU/长任务/大文件）与主应用完全不同，且 AI 网关是安全隔离边界。

**代价**：无法按模块独立扩容。对 200 并发无影响。

### C-03 并发规模：1000 还是 200

| 出处                       | 数字                      |
| ------------------------ | ----------------------- |
| `软件需求规格说明书_V2.0` §5.1    | 并发用户 ≥1000              |
| `需求文件0517`（V3.1，更晚） §1.4 | 在线峰值 200 人，并发请求 100 QPS |

**裁决：按 200 在线 / 100 QPS 设计，容量按 300 在线 / 150 QPS 留余量。1000 判定为笔误或过度设计。**

**理由**：全公司 121 人，含外包与临时工约 216 人；200 在线已是全员 90% 同时在线的极端值。按 1000 设计会带来完全不必要的部署成本（多节点、分布式缓存、读写分离）。

**但保留扩容触发条件**（写进 15 册）：在线 >250 持续一周，或 QPS >120 持续一小时，则启动应用无状态化 → 双节点 + Nginx 分流。

### C-04 库存权威源：T+ 还是本地

| A                                                                 | B（上一版）                 |
| ----------------------------------------------------------------- | ---------------------- |
| **T+ 是库存权威数据源，ProjLife 不维护自己的库存数量表**，本地仅 Redis 缓存 5 分钟（0517 §9.1） | 本地为权威，扫码即记账，推送 T+ 生成单据 |

**裁决：采 A 的"T+ 权威"原则，但补上 B 的"扫码即记账"，用「事务流水本地、账面数量 T+、每日对账」三者组合。**

具体机制（这是本规格包最关键的技术设计之一）：

```
现场扫码出库
  → 本地写 inv_transaction（status=PENDING_SYNC，含 idempotency_key）
  → 同步调 T+ 出库接口
      ├─ 成功：回写 t+_voucher_no，status=SYNCED，扣减 inv_stock_cache
      └─ 失败：status=PENDING_SYNC 留在队列，job-worker 指数退避重试 3 次
              └─ 仍失败：status=EXCEPTION，进"待人工处理"，界面可重试/可导出
  → 每日 23:00 对账：Σ本地事务 vs T+ 出入库流水，差异入 inv_reconcile_diff
```

**理由**：① 财务只认 T+ 的账，若本地另立权威，必然出现"两套数"；② 但纯 T+ 方案下"单据滞后"问题无解（T+ 需要人工回系统录单），B 的诊断正是这个病根。扫码产生本地事务再推 T+，把"记账动作嵌入业务动作"，同时不争夺权威。

**代价**：库存查询有 ≤5 分钟缓存延迟；T+ 接口不可用时出库转"挂起"状态，需要业务侧容忍（写进 SOP）。

### C-05 移动端：微信小程序还是 PWA

| A                                         | B（上一版）                               |
| ----------------------------------------- | ------------------------------------ |
| 微信小程序（uni-app），第三方施工人员**只能**用小程序，PC 端拒绝登录 | PWA（Service Worker + IndexedDB 离线队列） |

**裁决：微信小程序为主（现场作业 + 第三方），H5 响应式页为辅（内部员工临时用）。**

**理由**：① 第三方施工人员账号必须限定端，这是数据安全要求（C-09 安全约束之一），PWA 无法做端限制；② 现场人员手机必装微信，小程序无需安装、可发模板消息；③ 但小程序离线能力受微信限制（Storage 上限、后台被回收），因此内部员工的扫码/销项用 H5 兜底。

**代价**：需申请小程序并完成企业认证；离线缓存上限约 200MB，图纸缓存要控制（只缓存已发布的 PDF 预览，不缓存原文件）。

### C-06 合同编号：两套规则

| A                                    | B                                                                      |
| ------------------------------------ | ---------------------------------------------------------------------- |
| `CON-YYYYMM-四位流水`（如 CON-202601-0001） | `{主体码}-{年度}-{性质码}-{业务码}-{4位流水}`（如 TLD-2026-CG-AZFWXF-0091），补充协议 `-BC1` |

**裁决：新签合同用 B 的规则（信息量更大、能区分买卖方向），A 的 CON 格式作为存量兼容与"简易合同"别名。**

**理由**：B 的规则来自《合同与项目信息建档管理办法》（2026-10-12），比 A 的 0517 晚 5 个月，且解决了一个 A 没解决的问题——销售合同与采购合同共用一套业务码，无法从编号判断买卖方向。B 增加的性质码 `XS/CG/KJ` 直接解决这个。

**兼容处理**：系统内 `contract_no` 存 B 规则，另设 `legacy_no` 字段存存量 CON 编号，检索时两者都匹配。

### C-08 组织规模：122 还是 121

| A（0517）                                                 | B（钉钉通讯录 2026-10-09）                                     |
| ------------------------------------------------------- | ------------------------------------------------------- |
| 122 人：技术中心 28（研发 10 + 集成 18）、工程技术部 24、企管部 6、仓储部 5、计划部 3 | 121 人：技术中心 27（研发 10 + 集成 17）、工程技术部 23、企管部 7、仓储部 4、计划部 4 |

### C-09 BOM：三视图还是三形态（**本次整合最有价值的一处**）

| A：BOM 三视图                   | B：BOM 三形态                   |
| --------------------------- | --------------------------- |
| EBOM 设计 → MBOM 制造 → SBOM 服务 | A 标准产品 / B 参数化定制 / C 系统集成项目 |

两者看似冲突，实则**正交**：视图回答"同一份 BOM 在哪个阶段长什么样"，形态回答"这个产品要不要建完整 BOM"。硬用一套会同时犯两个错——A 的错误是给系统集成项目也建 MBOM（实际没有制造过程），B 的错误是给升降机也只想建一份清单（实际设计/工艺/服务三个视角都要）。

**裁决：二维矩阵建模。**

| 形态 ↓ / 视图 →                | EBOM（设计）                 | MBOM（制造）                               | SBOM（服务）                |
| -------------------------- | ------------------------ | -------------------------------------- | ----------------------- |
| **A 标准产品**（升降机/免爬器/自动盖板）   | 完整两级：整机→部件总成→零件          | 由 EBOM 转，加工艺辅料与工序顺序                    | 由 EBOM 裁剪，只留可更换件与安全件    |
| **B 参数化产品**（爬梯/导轨）         | 模板 + 参数（塔高/节数/段长）自动展开    | 同左，加工序                                 | 按项目实例生成备件清单             |
| **C 系统集成项目**（视频监控/自动消防/技改） | 工程物料清单，按点位（机舱/塔底/塔筒/升压站） | **不建**（无制造过程，标记 `mbom_not_applicable`） | **= 设备档案**（一机一档，售后维修依据） |

**这带来三个直接好处**：

1. C 类项目不必建 MBOM，但必须在界面明确标注"不适用"，而不是留空让人以为漏了；
2. **SBOM = 设备档案**，A 想要的"机组全生命周期档案"与 B 想要的"工程 BOM 一份三用"合并成一个实体，不再各建一套；
3. 参数化产品（B 类）的 EBOM 是"模板"，MBOM 也是模板，只有项目实例才展开——避免了 B 方案里"每个订单手工建 BOM"的坑。

### C-10 看板：九板还是三层

| A                             | B                           |
| ----------------------------- | --------------------------- |
| 总经理看板 / 板块看板 / 个人工作台（三层，按角色切） | 1+4+4 九板（按价值链切）+ 四区一栏 + 红灯卡 |

**裁决：九板为主（B），个人工作台为入口（A），A 的"总经理看板"就是 B 的①公司经营总看板。**

**理由**：A 的三层看板是"按组织层级切"，会导致同一件事在不同层级重复统计；B 的九板是"按价值链切"，链主对全链负责，交界处的问题不会"每块板都看得见、每块板都不负责"。A 的唯一增量是"个人工作台"——它是入口，不是看板，应保留。

**合并后的看板体系**：

```
① 公司经营总看板（总经理部，周）      ← A 的"总经理看板"升级版
②③④⑤ 四张业务链日板（订单/供应链/生产/工程）
⑥⑦⑧⑨ 四张职能周板（研发/市场销售/财务/企管）
＋ 个人工作台（每人的入口：我的卡/我的任务/我的审批）
＋ 板块看板（A 的"业务板块负责人"视角：可订阅任意几块板的组合视图，不新增板）
```

### C-11 生产管理深度：工序级还是最小字段

| A                           | B（上一版）                         |
| --------------------------- | ------------------------------ |
| 工序级报工 + Andon + 物料防错 + 工艺参数 | 只建最小字段（工单号/计划完工/实际完工/状态），由内勤维护 |

**裁决：采用 A 的工序级。** 我上一版的"最小字段"降级是错误的。

**理由**：生产部 20 人是全公司第二大部门；B 的 BOM 审计发现"工艺落线"缺口（导轨 0%、自动消防 4.7%），根因是"工艺文件不是随产品强制产出物"，只有把工序搬到系统里、报工必须过工序，工艺文件才真正被使用。最小字段方案会让这 20 人继续在 Excel 里报工。

**代价**：MES 是本期工作量最大的一块（估算占总量 20%），且需要工艺部先把工序路线整理出来（这是业务前置条件，不是技术问题）。

### C-12 AI 能力：内网双模型

| A                                        | B（上一版） |
| ---------------------------------------- | ------ |
| 数据推理模型 + 图像识别模型，**内网私有化部署，严禁调用公网 AI 服务** | 未涉及    |

**裁决：完全采用 A。** 并补三条 A 没写清的内容：

1. **无模型时的完整降级链**：模型不可用 → 返回"人工模式"（表单可手工填，AI 结果区显示"待人工录入"）→ 不阻塞业务；而不是只返回"服务繁忙"。
2. **AI 结果的复核闭环**：所有 AI 输出必须标 `ai_generated=true` + 置信度 + 模型版本；人工修改后标 `human_corrected=true` 并记录差异——这是模型迭代的训练数据来源。
3. **AI 失败率与采纳率作为验收指标**（见 13 册），而不是只验收"接口通了"。

## 七、全局约定

### 7.1 编号体系

| 前缀            | 含义            | 示例                 |
| ------------- | ------------- | ------------------ |
| `FR-{域}-{序号}` | 功能需求          | FR-CT-012 合同编号自动生成 |
| `BR-{nn}`     | 全系统硬卡点（仅 9 处） | BR-01 合同评审必须带项目编码  |
| `NFR-{nn}`    | 非功能需求         | NFR-03 列表查询 ≤1s    |
| `UC-{域}-{nn}` | 验收用例          | UC-CT-04           |
| `T-{域}-{nn}`  | 实体表           | T-CT-03 合同档案       |
| `E-{nn}`      | 枚举            | E-12 合同状态          |
| `AI-{nnn}`    | AI 接口         | AI-001 合同风险分析      |
| `C-{nn}`      | 冲突裁决（仅 00 册）  | C-04 库存权威源         |

### 7.2 九处硬卡点（全系统仅此九处，其余一律零阻力）

| 编号    | 卡点                    | 来源            | 拦截行为          |
| ----- | --------------------- | ------------- | ------------- |
| BR-01 | 合同评审必须带项目编码           | B 归口办法        | 拒绝提交，给"去建档"入口 |
| BR-02 | 用印后 3 个工作日未建档，冻结开票    | B 建档办法        | 开票申请 422      |
| BR-03 | 无项目编码不得排产、派工、发货、报销    | B 归口办法        | 四类单据统一校验      |
| BR-04 | 派工单不选风场不许提交           | B 归口办法        | 弹窗二选一         |
| BR-05 | 安全件补货可先发后签，24h 内必须补齐  | B 库房方案        | 超时锁定新申请       |
| BR-06 | 非授权角色不得见采购单价/合同金额/成本  | A 脱敏规则        | 服务端返回 null    |
| BR-07 | 文件下载只能拿到带水印 PDF，禁原始文件 | A 文件安全        | 拒绝原文件请求       |
| BR-08 | 第三方施工人员只能登录小程序，PC 端拒绝 | A 端限制         | PC 登录返回 403   |
| BR-09 | BOM 变更未附旧料处置方案，拒绝提交   | B 库房方案+BOM 审计 | 拒绝 ECN 提交     |

> 设计原则：**卡点越少越有效**。B 的经验是"一个硬卡点胜过十条倡导"，A 的 4 条安全约束属不可协商项，因此合并为 9 处，任何新增必须走变更评审。

### 7.3 技术约定

| 项     | 规定                                                                                                    |
| ----- | ----------------------------------------------------------------------------------------------------- |
| 数据库   | GreatDB（MySQL 8.0 兼容），`utf8mb4` / `utf8mb4_unicode_ci`                                                |
| 主键    | `BIGINT AUTO_INCREMENT`，业务编码独立字段（不把编码当主键）                                                             |
| 软删除   | `deleted TINYINT DEFAULT 0`（1=已删），**所有业务表**；审计日志表不软删                                                  |
| 审计字段  | `created_by VARCHAR(64)`、`created_at DATETIME`、`updated_by VARCHAR(64)`、`updated_at DATETIME`（按 A 规范） |
| 金额    | `DECIMAL(18,2)`，单位**元**；禁止 float/double                                                               |
| 数量    | `DECIMAL(14,3)`                                                                                       |
| 比例/税率 | `DECIMAL(6,4)`（0.1300 = 13%）                                                                          |
| 时间    | `DATETIME`，服务器时区 `Asia/Shanghai`                                                                      |
| 枚举    | 存英文大写 code（如 `SIGNED`），字典表维护中文 label                                                                  |
| JSON  | MySQL `JSON` 类型；**不建索引**，需要检索的字段必须拆列                                                                  |
| 接口    | RESTful，`/api/v1/{module}/{resource}`，统一响应包                                                           |
| 认证    | JWT（access 2h + refresh 7d），Redis 存黑名单                                                                |
